# 6R.48 — QualByDepth RNG stream (process-global Java `Random`)

Pinned Java: GATK **4.4.0.0** SHA `2dbc025821bc5f686c423ff332a41e6cef892a77`.  
One production semantic: QualByDepth jitter uses one process-global stream and is applied
in genomic emit order. Mid-B not reopened except as regression control.

**Classification: B — RNG lifecycle/seeding divergence** (not A: `GatkJavaRng` already matched Java).

## Java source contract

`QualByDepth.java` / `Utils.java` at the pinned SHA:

- `annotate` runs **once per `VariantContext`**, not per allele or genotype.
- Depth 0 / missing QUAL / empty genotypes → empty INFO map → **no Gaussian**.
- Else `QD = QUAL / depth`, then `fixTooHighQD(QD)`.
- `fixTooHighQD`: if `QD < 35` return unchanged (**no draw**); else
  `30 + Utils.getRandomGenerator().nextGaussian() * 3`.
- Annotate formats with `String.format("%.2f", QD)`. QualByDepth makes **no** other
  `nextInt` / `nextDouble` / `nextGaussian` calls.
- `Utils.randomGenerator` is `private static final Random(47382911L)` — **one JVM-static
  stream** for the process. `resetRandomGenerator()` reseeds; HC does not reseed per
  contig, VCF, or site. `getRandomDataGenerator()` (Well19937c) is a **different** object
  and is not used by QualByDepth.
- The HC walker is sequential; annotation order is variant emit order (assembly-region
  traversal, then sites within the region). PairHMM threads do not create a second QD stream.

Reservoir downsampling (`ReservoirDownsampler`) **does** call `nextInt` on the same static
`Random`. On `p12_snp_cluster` that consumption is not visible: the first four QDs are the
fresh-stream prefix, and the 716-cluster is draws 5–9 of that same prefix.

## RNG implementation (hypothesis A)

Independent of production emit: `GatkJavaRng` seed `47382911`, `nextGaussian()`, then
`30 + g * 3` formatted `{:.2}`:

```
25.36  28.73  30.97  27.24  28.20  25.00  29.56  30.62  28.17
```

Matches 6R.41 and the Java VCF prefix. **Do not change the RNG implementation.**

## Draw eligibility / order (hypotheses D/E/F)

## Rust pre-fix behavior

`thread_local!` `GatkJavaRng` seeded at `47382911`, jitter inside `annotate_hc_variant_site`
during `into_par_iter` region emit. Each Rayon worker initialized a **fresh** stream.
`reset_gatk_qual_by_depth_rng` at `run_haplotype_caller` start only reset the calling thread.

Interval `2:92305500-92305850` is one HC process (fresh seed). Two ActiveFulls; all nine
sites have raw QD ≥ 35 (78.32/2 and 116.84/3).

| | Java (one stream) | Rust pre-fix |
|--|-------------------|--------------|
| Draws before 716-cluster | **4** | **0** (reseed) |
| First differing ordinal | **5** | **1** of a new stream |
| Site | `2:92305716 A/C` | same site |
| Gaussian → printed QD | draw 5 → **28.20** | draw 1 → **25.36** |

Java 716-cluster QDs `28.20, 25.00, 29.56, 30.62, 28.17` are draws 5–9. Rust pre-fix
repeated `25.36, 28.73, 30.97, 27.24, 28.20` (draws 1–5 of a second TLS stream).

Not hypothesis C (interleaved order) and not E (reservoir `nextInt` between clusters):
the 716-cluster was a **restart**, not a shifted ordinal.

Test-only `QdDrawTrace` (crate-private, `cfg(test)`) records site, raw QD, eligibility,
ordinal, Gaussian, result, and stream position. Not a public API. No custom GATK Java
build; Java ordinals are from source + VCF (nine consecutive eligible sites).

## Production change

1. Process-global `Mutex<GatkJavaRng>` matching `Utils.randomGenerator`.
2. `annotate_hc_variant_site` stores **raw** QUAL/depth.
3. Parallel VCF emit (`try_emit_call_region_variants_raw_qd`) does not jitter.
4. `merge_region_emit_batches` applies `fixTooHighQD` when inserting records in
   contig / start / `region_index` order (Java walker order).
5. Single-region tests / sequential gVCF still jitter at emit time (same process stream).

Did **not**: hard-code QD, seed per site/chr/VCF, reset per annotation, force
`GATK_RS_HC_SEQUENTIAL=1`, share the stream with reservoir, change QUAL / AF / EventMap /
trim / graph.
