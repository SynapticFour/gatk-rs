# 6R.46 — haplotype trim vs `p12_snp_cluster`

Pinned Java: GATK **4.4.0.0** SHA `2dbc025821bc5f686c423ff332a41e6cef892a77`.  
6R.45 retention is unchanged. **No production trim change.**

## Verdict

**IMPLEMENTATION_DIVERGENCE** — not in `AssemblyRegionTrimmer` / `Haplotype.trim`.

The `77M` vs `28M171D75M` phenotype is real, but it is a **consequence** of the trim **input** (variation events), not of the trim interval math or CIGAR slice.

## First divergence

**Stage F EventMap**, function `variation_events_for_haplotype` (`event_map.rs`).

Rust drops the 171 bp deletion because `REF.len() == 172 > MAX_VARIATION_EVENT_ALLELE_LENGTH` (**40**). Java `EventMap.processCigarForInitialEvents` has no such cap.

Given SNP-only events, Stage G is Java-equivalent and then **drops** `28M171D160M` because the padded window starts inside the D.

| | Java (bamout / inferred) | Rust |
|--|--------------------------|------|
| untrimmed hap | `28M171D160M` (retained 6R.45) | `28M171D160M` retained |
| assemble EventMap | **must include 171D** (else Java could not pad to 92305424–92305697) | 9 SNPs only; **no 171D** |

Proven: trimming the same Rust haplotype to the Java-inferred span **does** yield `28M171D75M`.

## Java contract (trim)

- `AssemblyRegionTrimmer.trim` (~171–208)
- `AssemblyResultSet.trimTo` → `trimDownHaplotypes(paddedSpan)` (~72–160)
- `Haplotype.trim` + `AlignmentUtils.getBasesCoveringRefInterval` / `trimCigarByReference`

6R.39 `maxEnd = Math.max` is **not** contradicted. Do not reopen it.
